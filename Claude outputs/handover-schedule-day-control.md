# Handover: Schedule Day Control (1.0.1 hotfix, batch 3)

## 1. Risk declaration

Risk Level: **Medium** (scheduling — changes the shape of `tournaments.schedule` and the
generator's behaviour).

This changes a documented contract: `docs/schedule.md`'s Day object shape gains a new
key, and the generator (`scheduleGenerator.js`) and the schedule maker's day strip both
need to honour it. Getting the default wrong would silently change every existing saved
schedule's behaviour (a missing key must default to "included", not "excluded", or every
tournament created before this ships loses days it already has entries on). This
document is the explanation CLAUDE.md's Medium Risk process requires.

## 2. How to use this document

Read Established Facts and Decisions fully before starting — the day model touches three
files that all need to agree on the same shape. Then do the steps in order; Step 2
depends on Step 1's shape existing.

## 3. Established facts

**`days` is currently derived, not chosen.** `docs/schedule.md` and
`tourganiser-ui/src/utils/scheduleUtils.js`'s `normaliseTournamentDays(startDate,
endDate, existingDays)` walk every calendar day between the tournament's `start_date` and
`end_date` and rebuild the `days` array **on every read**, keeping only the stored `id`
and `label` for any date still in range from `existingDays`. There is currently no way
to have a day inside the tournament's date range be absent from `days` — every day in
range always exists as a day object today.

**One choke point builds the generator's candidate slots.**
`tourganiser-ui/src/utils/scheduleGenerator.js`:

```js
function buildCandidateSlots(days, courts, startTime, endTime, durationMinutes) {
	...
	days.forEach((day) => {
		for (let cursor = firstMinute; cursor + durationMinutes <= dayEndMinutes; cursor += durationMinutes) {
			...
		}
	});
	...
}
```

called as `buildCandidateSlots(schedule.days, courts, ...)` (~line 620). Every candidate
slot the generator will ever place a fixture into comes from this one function iterating
`days`. This is the single place that needs to skip a day, rather than something spread
across the generator.

**The day strip is one render site.** `ScheduleMakerModal.jsx`'s
`.schedule-maker-day-tabs` (~line 1221) renders `schedule.days.map((day) => ...)` as the
tab list the organiser switches between to see one day's grid. `activeDay` state
(~line 228) defaults to `schedule.days[0]?.date`. `schedule.days` is also read in at
least two other render sites (~line 1834, ~1965, ~2074) — the settings form and the
print-export headers respectively; check each when implementing to see whether it needs
to filter out excluded days too (the print export in particular should almost certainly
skip a day nothing can be scheduled on).

**A day-level settings form already exists**, around ~line 1797, with a `dayStartTime`
time input as part of a settings draft (`draft`/`onChange` props, `settingsDraft` state
built from `schedule.settings`). This is the organiser-facing place schedule-wide
settings (start/end time, slot length) are currently edited. `GeneratorPanel` (~line
1876) is a separate panel specifically for generation options (e.g. the officials
auto-assignment toggle lives there, per `docs/roadmap.md`).

**Nothing here is validated server-side that's been confirmed.** `docs/schedule.md`
documents the server rejecting entries outside the tournament's date range, but whether
it separately checks anything about which specific days are "in use" hasn't been
confirmed in this planning session — verify against the actual validator
(`api/src/utils/scheduleValidator.js` or wherever it lives) before assuming only the
client-side generator needs to change.

## 4. Decisions already made

- **One mechanism serves both framings Tom asked for.** Every day in the tournament's
  date range is still generated by `normaliseTournamentDays` exactly as today (no
  regression to what days exist), but each day object gains a new key, `enabled`
  (boolean). The UI presents this as a set of day chips/rows the organiser taps to
  include or exclude — which reads equally well as "a toggle per day" (Tom's first
  framing) and as "explicitly choosing which days are game days" (his second), since
  toggling a day off and on again *is* adding/removing it from the active set. This
  avoids introducing a second, competing notion of "which days exist" alongside the one
  that already exists.
- **Default is `true` (included) for every day, always**, both for a brand-new schedule
  and for `enabled`'s absence on any day coming from an old saved schedule that predates
  this key. This preserves current behaviour exactly for every tournament that hasn't
  touched the new control — the same pattern `docs/schedule.md` already documents for
  `courts[].divisions` ("absent or empty means unrestricted").
- **A disabled day is skipped by the generator entirely** (contributes no candidate
  slots) but **is not removed from `schedule.days`** — it stays present, just excluded,
  so re-enabling it is a toggle, not a "day 4 has vanished, how do I get it back"
  problem. Hand-placement onto a disabled day should also be blocked — a disabled day
  has no meaningful slots to drop a fixture on, consistent with the generator's own
  treatment of it.
- **Placement of the toggle UI**: use judgement per the intent above rather than a
  pixel-exact spec. A reasonable approach is to make each day tab itself carry the
  toggle (long-press/right-click/an inline control on the tab), or to add the day list
  to the existing settings form near `dayStartTime` (~line 1797) as a set of togglable
  rows/chips — either satisfies the requirement. Whichever is chosen, a disabled day's
  tab should be visually distinguishable from an enabled one (not simply hidden — the
  organiser needs to be able to find and re-enable it).

## 5. Non-goals

- Don't change how `start_date`/`end_date` define the tournament's overall date range —
  that's unrelated and out of scope. This is about which days *within* that range are
  active for scheduling, not about shrinking or growing the range itself.
- Don't touch `dayStartTime`/`dayEndTime`/`slotMinutes` — those already work per-schedule
  (not per-day) and stay that way.
- Don't attempt per-day start/end times — not asked for, and a materially bigger change
  than this one.
- Don't change the print export's per-day pagination logic beyond skipping disabled
  days — anything about how a printed day is laid out belongs to the schedule
  access/print handover, not this one.

## 6. Numbered steps

### Step 1 — Add `enabled` to the day model

**Why:** the generator, the day strip, and anything reading `schedule.days` need a
place to find out whether a day is active.

**Files:** `tourganiser-ui/src/utils/scheduleUtils.js`, `docs/schedule.md`.

**Do:**
- In `normaliseTournamentDays`, add `enabled: day.enabled !== false` (or equivalent —
  defaults to `true` unless explicitly `false`) to each generated day object, sourced
  from the matching entry in `existingDays` the same way `label` already is.
- Update `docs/schedule.md`'s Day table to document the new key, its type, default, and
  meaning, following the existing style of that table (see the `courts[].divisions` row
  for the closest precedent — "optional... absent or empty means X").

**Don't:** don't change `buildEmptySchedule` or `normaliseSchedule`'s signatures — this
only adds a key inside the day objects they already produce.

**Verify:**
- A brand-new schedule (no prior `days` stored) has every day `enabled: true`.
- An old saved schedule with no `enabled` key on its stored days normalises to
  `enabled: true` for all of them — no regression.
- Toggling a day off, saving, reloading the tournament — the day comes back `enabled:
  false`, not reset to `true`.

### Step 2 — Wire the toggle into the UI and the generator

**Why:** `enabled` needs a way to be set by the organiser, and a way to actually change
what the generator does.

**Files:** `tourganiser-ui/src/components/ScheduleMakerModal.jsx`,
`tourganiser-ui/src/utils/scheduleGenerator.js`, and the relevant stylesheet
(`schedule-maker.css`).

**Do:**
- Add the toggle control per Decisions above, wired to update the day's `enabled` value
  in schedule state (following whatever pattern the existing settings form/day tabs use
  to mutate schedule state — don't invent a new one).
- In `scheduleGenerator.js`, filter `days` to `enabled !== false` before or inside
  `buildCandidateSlots` (a `.filter()` on the `days` array passed in, or as the first
  line inside the function — either is fine, prefer whichever reads more clearly against
  the surrounding code).
- Block hand-placement (drag-and-drop, or the "open slot" click path) onto a disabled
  day's slots. Locate wherever the schedule grid currently decides a slot is a valid
  drop target and add the day's `enabled` state to that check.
- Check the print-export render sites (~line 1965, ~2074) and skip a disabled day's page
  entirely, the same way a day with zero entries presumably already would (or add the
  check if it doesn't).
- Check the server-side schedule validator per Established Facts above — if it validates
  entries against something day-related beyond "inside the date range", confirm a
  disabled day doesn't need separate server-side enforcement (an organiser could in
  principle craft a request placing an entry on a disabled day directly against the API,
  bypassing the client UI — decide whether that's worth guarding server-side or whether
  it's acceptable that the client is the only gate, consistent with how much else in this
  app's scheduling is client-enforced only, per `docs/architecture.md`'s note that the
  generator "stays in the client").

**Don't:** don't change the generator's hard-constraint list
(`docs/schedule.md`, "Generation objectives") beyond adding this filter — rest, court
exclusivity, round order etc. are all unaffected and unrelated.

**Verify:**
- Disable one day of a multi-day tournament, run "Generate" — no fixture is placed on
  the disabled day; fixtures that would have gone there either land on an enabled day or
  show up in the unscheduled list with a sensible warning (reuse whatever the existing
  "ran out of room" warning path already does, per `scheduleGenerator.js`'s warning
  messages).
- With a day disabled, attempt to drag a fixture directly onto that day's grid (if the
  UI still shows it at all per the visual-distinguishability requirement above) — the
  drop is rejected the same way an otherwise-invalid drop already is.
- Re-enable the day — it becomes schedulable again immediately, no reload needed.
- A tournament schedule generated and saved *before* this change loads with all days
  enabled and behaves exactly as before.

## 7. Final validation

- `npm run test` from `tourganiser-ui/` — `scheduleUtils` and `scheduleGenerator` are
  both covered by the pure-module test suite; add or extend tests for the new `enabled`
  behaviour rather than only hand-verifying.
- `npm run lint` — confirm the pre-existing error count (5) has not grown.
- `npm run build` — confirm it still succeeds.
- Walk the Step 2 Verify list once more end-to-end: disable a day, generate, save,
  reload, confirm the disabled state and the schedule both persisted correctly.
